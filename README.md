# Сервис формирования цифрового признака ТС

Готовое к развёртыванию решение: backend инференса с OpenAPI, СУБД для базы эмбеддингов
и веб-интерфейс. **Каталог самодостаточен**: код модели (`reid/`), конфиги (`configs/`)
и веса (`weights/`) лежат внутри — сервис можно сдавать и разворачивать отдельно от
обучающих скриптов.

## Запуск без Docker

```bash
python service/run_local.py
```

Поднимает backend и интерфейс, ждёт загрузки модели и печатает адреса. `Ctrl+C` останавливает оба.
Полезные флаги:

```bash
python service/run_local.py --api-only              # только backend
python service/run_local.py --port 8000 --ui-port 8501
python service/run_local.py --data-root D:/data/Датасет
python service/run_local.py --reload                # перезапуск backend при правке кода
```

Хранилище по умолчанию — SQLite (`service/data/gallery.sqlite`), отдельная СУБД не нужна.
Зависимости: `pip install -r service/requirements-api.txt -r service/requirements-ui.txt`
плюс torch под вашу CUDA (см. корневой README).

## Запуск в Docker

```bash
cd service
docker compose up --build
```

| компонент | адрес | что это |
|---|---|---|
| Веб-интерфейс | http://localhost:8501 | тонкий клиент: инструкция, пакетная обработка, поиск по фото, эксперименты |
| Swagger UI | http://localhost:8000/docs | интерактивная документация API |
| ReDoc | http://localhost:8000/redoc | альтернативный просмотр спецификации |
| Спецификация OpenAPI | http://localhost:8000/openapi.json | машиночитаемая, версия 3.1.0 |

Набор данных монтируется только на чтение из `../../Датасет` (см. `docker-compose.yml`,
секции `volumes`). Веса модели входят в образ — при работе интернет не нужен.

### Компоненты по отдельности

```bash
cd service
python -m uvicorn api.main:app --port 8000                       # backend
API_URL=http://localhost:8000 streamlit run ui/app.py            # интерфейс
```

## Архитектура

```
              браузер (тонкий клиент)
                       │ HTTP
        ┌──────────────▼──────────────┐
        │  ui   Streamlit, 8501       │   логики нет, только вызовы API
        └──────────────┬──────────────┘
                       │ HTTP (OpenAPI)
        ┌──────────────▼──────────────┐
        │  api  FastAPI + модель, 8000│   инференс, ранжирование, режим отказа
        └──────────────┬──────────────┘
                       │ SQL
        ┌──────────────▼──────────────┐
        │  db   PostgreSQL + pgvector │   эмбеддинги галереи и метаданные
        └─────────────────────────────┘
```

Три независимых сервиса в `docker-compose.yml`. Компоненты общаются только по сети,
поэтому любой можно заменить или масштабировать отдельно.

```
service/
  run_local.py              запуск без Docker: backend + интерфейс
  docker-compose.yml        три сервиса: db, api, ui
  Dockerfile.api            backend (контекст сборки — сам service/)
  Dockerfile.ui             интерфейс
  api/
    main.py                 методы API, из них генерируется OpenAPI
    engine.py               загрузка модели и извлечение эмбеддингов
    store.py                хранилище: PostgreSQL+pgvector или SQLite
    schemas.py              схемы запросов и ответов (pydantic)
    settings.py             настройки через переменные окружения
  reid/                     код модели: тот же, которым она обучалась (+ gradcam.py)
  configs/
    ensemble.yaml           итоговая модель сервиса
    member_*.yaml           члены ансамбля
  weights/                  веса (368 МБ)
  ui/
    app.py                  точка входа и навигация
    common.py               общее для страниц: адрес API, обёртки
    views/home.py           как пользоваться
    views/batch.py          каталог с данными → артефакты сдачи
    views/search.py         база, поиск по снимку и Grad-CAM
    views/experiments.py    журнал экспериментов с графиками
  data/                     база SQLite и результаты пакетной обработки
```

Названия файлов латиницей; заголовки страниц в меню задаются в `ui/app.py` через `st.Page`.

## Методы API

| метод | назначение |
|---|---|
| `GET /health` | состояние, параметры модели и галереи |
| `POST /embed` | эмбеддинг по изображению и bbox |
| `POST /gallery/bulk` | проиндексировать галерею из CSV |
| `POST /gallery/items` | добавить один снимок |
| `GET /gallery/stats` | размер и параметры базы |
| `DELETE /gallery` | очистить базу |
| `DELETE /gallery/items` | удалить снимки по идентификаторам |
| `POST /search` | поиск по снимку с режимом отказа |
| `POST /jobs/batch` | сформировать `submission.csv`, `candidates.csv`, `embeddings.npy` |
| `POST /explain` | Grad-CAM: PNG с областями, определившими сходство |

Пример: наполнить базу и найти ТС по снимку.

```bash
curl -X POST http://localhost:8000/gallery/bulk \
  -H 'Content-Type: application/json' \
  -d '{"csv_path":"/data/dataset/test_gallery.csv","replace":true}'

curl -X POST http://localhost:8000/search \
  -F "file=@frame.jpg" -F "bbox=1309,65,609,483" -F "top_k=10" -F "threshold=0.3"
```

Ответ при отказе (в галерее нет уверенного совпадения):

```json
{ "matched": false, "threshold": 0.3, "best_score": 0.206,
  "vehicle_id": null, "refusal_reason": "лучшее сходство 0.206 ниже порога 0.30",
  "candidates": [ {"image_id": "...", "score": 0.206, "accepted": false} ] }
```

## Интерпретируемость: почему модель так решила

`POST /explain` строит тепловую карту Grad-CAM: дифференцируется **косинусное сходство
эмбеддинга запроса с эмбеддингом кандидата** по карте активаций последнего блока backbone.
Тёплые области — те, без которых сходство упало бы.

Сходство симметрично, поэтому по умолчанию (`mode=pair`) карта строится для **обоих**
снимков: карта запроса — относительно эмбеддинга кандидата, карта кандидата — относительно
эмбеддинга запроса. Так видно, смотрела ли модель на соответственные части (например, на
линию крыши у обоих), а не на кузов у одного и на фон у другого. Режимы `side_by_side`
и `overlay` дают карту только для запроса.

У ансамбля карты обоих членов усредняются, подложка обесцвечивается (иначе на красном
кузове карту не отличить от собственного цвета машины).

```bash
curl -X POST http://localhost:8000/explain   -F "file=@frame.jpg" -F "bbox=1309,65,609,483"   -F "reference_image_id=29a63a51405d4384ba62046f24e3d5f9" -o gradcam.png
```

В заголовках ответа: `X-Reference-Image-Id`, `X-Score`, `X-Explain-Mode`, `X-Members-Used`,
`X-Focus-Center-Share` и `X-Focus-Peak-Area` для запроса, а в режиме `pair` ещё и
`X-Focus-Center-Share-Reference`, `X-Focus-Peak-Area-Reference` для кандидата. «Доля
важности в центре» считается по центральным 70% кропа: низкое значение означало бы, что
модель цепляется за фон.

В интерфейсе — кнопка «Построить карту» на странице поиска, с выбором кандидата
и режима отображения. Реализация — `reid/gradcam.py`.

## Какая используется СУБД

Зависит от `DATABASE_URL`:

| режим | что используется | когда |
|---|---|---|
| `DATABASE_URL` не задан | **SQLite** — файл `service/data/gallery.sqlite`, поиск матмулом в numpy | `run_local.py`, разработка, демонстрация без Docker |
| `DATABASE_URL=postgresql://…` | **PostgreSQL + pgvector**, HNSW-индекс по косинусу | `docker compose up` — так задано в `docker-compose.yml` |

База сохраняется между запусками в обоих режимах: SQLite — файл на диске, PostgreSQL —
том `db_data`. Индексировать галерею заново после перезапуска не нужно; текущее
расположение базы видно в `GET /gallery/stats` и в боковой панели интерфейса.
Повторная загрузка того же CSV по умолчанию не очищает базу, а обновляет записи
(`replace: false`), поэтому операция идемпотентна.

Оба варианта — реляционные СУБД, что соответствует ТЗ §6. Интерфейс у них общий
(`api/store.py`), переключение — одной переменной окружения, код вызывающей стороны
не меняется. На галерее до ~100 тысяч объектов brute-force поиск в SQLite-варианте
быстрее ANN (0.43 мс на 10 000 объектов), поэтому это не «заглушка», а рабочий режим;
pgvector нужен, когда база растёт и хочется индекс и сетевой доступ к ней.

## Настройки (переменные окружения)

| переменная | по умолчанию | смысл |
|---|---|---|
| `MODEL_CONFIG` | `configs/ensemble.yaml` | какой конфиг модели загружать (относительно `service/`) |
| `DATABASE_URL` | — | DSN PostgreSQL; пусто → SQLite |
| `SQLITE_PATH` | `service/data/gallery.sqlite` | файл базы для SQLite |
| `PCA_DIM` | `256` | размерность хранения; `0` — полный эмбеддинг |
| `DEFAULT_THRESHOLD` | `0.30` | порог режима отказа |
| `DATA_ROOT` | `../../Датасет` | каталог с данными на стороне сервиса |
| `OUTPUT_DIR` | `service/data/outputs` | куда писать артефакты пакетной обработки |
| `SERVICE_DIR` | каталог сервиса | база для относительных путей |
| `DEVICE` | автоматически | `cuda` или `cpu` |
| `API_URL` (для ui) | `http://localhost:8000` | адрес backend |

## Два режима поиска — и почему они разные

| режим | как ищет | mAP@10 | задержка при базе 10 тыс. |
|---|---|---|---|
| онлайн (`POST /search`) | косинус по PCA-256 | 0.857 | 0.43 мс |
| пакетный (`POST /jobs/batch`) | косинус + k-reciprocal re-ranking | **0.894** | 0.26 мс/запрос |

Re-ranking даёт +3.4 pt, но **только когда запросы обрабатываются пакетом**: его выигрыш
берётся из связей между запросами. На одиночном запросе он не помогает, а ухудшает
результат — поэтому в онлайн-поиске не применяется, и API отклоняет такой вызов
с объяснением. Подробности и замеры — в `../EXPERIMENTS.md`, §9.1.

Почему эмбеддинг хранится после PCA до 256-d: в онлайн-режиме это стоит 0.3 pt mAP@10,
но даёт 20-кратную экономию памяти и времени поиска, и укладывается в ограничение
pgvector на размерность индексируемого вектора (2000). Полная размерность (5632-d)
используется в пакетном режиме, где важна каждая десятая пункта.

## Порог режима отказа

По умолчанию **0.30** — максимум F1 на размеченной выборке. Порог задаётся в запросе,
поэтому под сценарий можно выбрать другую рабочую точку:

| режим эксплуатации | порог | точность | полнота | доля запросов с ответом |
|---|---|---|---|---|
| подсказка оператору | 0.30 | 0.78 | 0.90 | 76% |
| баланс | 0.35 | 0.84 | 0.83 | 67% |
| высокая точность | 0.45 | 0.91 | 0.65 | 50% |
| решение без человека | 0.60 | 1.00 | 0.39 | 28% |

Обоснование и методика — `../EXPERIMENTS.md`, §7.2.
